Case Study

Job Tracker · August 2026 · Bahasa Indonesia

Job Tracker records job applications: free, ad-free, self-hosted. Built by one person, from a static interface to a service other people rely on. This page covers the decisions behind it and — the part people write up less often — the defects that reached production, and how each one was finally caught.

The problem

An active job seeker can have dozens of applications running at once, each at its own stage, with its own schedule, contacts and CV version. Without a tool the outcome is always the same: forgetting where you already applied, missing an interview, never knowing when following up is appropriate, and after three months being unable to answer the question that matters most — which stage am I actually losing at?

A spreadsheet solves part of it, but it does not remind you, does not hold your documents, and does not count anything.

Constraints chosen on purpose

Most decisions here were decisions not to add something.

  • Six runtime dependencies. Express, cookie-parser, Drizzle, mysql2, aws4fetch, zod. No animation library, no React icon library, no scheduler framework. Every new package has to justify itself first.
  • One Node process, serving /api/* and the static files together. No Docker, no Redis, no job queue, no staging environment.
  • No third-party trackers. No analytics, no ad pixels, no session recorders. The contents are a list of companies someone is applying to — often while still employed somewhere else.
  • No data import. Export is a way out, not a way back in. Import demands validating foreign files and a write path that can corrupt existing data, and not one user has asked for it.

Document files never pass through the Node process. The browser uploads straight to object storage through a short-lived signed URL, and downloads through a redirect to another one. That is why shared hosting with modest memory never chokes on a 2 MB file.

The expensive defects

Every one of these passed type checking and linting in silence. The types were right and the behaviour was wrong — which is exactly the class of defect that is hardest to find.

A security policy blocked every document upload

A newly added content security policy broke every upload in production, and it surfaced only through a user report. The cause was one harmless-looking line: turning a file already read into memory into a binary object by way of a network request. Browsers classify that as a connection, so the policy applied — and all the user saw was “failed”, with nothing naming the cause.

Why it slipped through: uploads had been tested by calling the API directly rather than through the page itself. Testing an endpoint is not testing a page.

One interview, two emails

The “interview tomorrow” reminder is scheduled for seven in the morning in the user's own timezone. The daily digest goes out at seven as well. Both ran independently, so a single interview produced two emails a minute apart carrying the same item.

No test caught it, because not one of them ran both jobs in the same morning. It was proven by running both against a user whose local hour was seven, and counting the emails that came out.

Deleting your data left the files behind

The “delete all data” button removed the database rows and never touched object storage. The files stayed forever — and once the rows were gone, nothing knew whose files they were, so nothing could ever clean them up.

Worse: account deletion decides whether it may proceed by counting those rows. After a reset the count is zero, the guard passes, and the files become unattributable garbage — precisely the outcome that guard exists to prevent.

Comparing against NULL always yields NULL

The daily digest claimed its work with a “not equal to today” comparison. A new user's value is empty, and in SQL a comparison against an empty value is neither true nor false. The result: the first digest for every user could never be sent — permanently, with no error anywhere. The function returned zero, indistinguishable from “nothing was due”.

It was found only by actually sending one. The earlier verification ran three queries by hand and all three were correct — the claim standing in front of them was never run at all.

Columns held UTC; the database's clock function returned local time

The application writes timestamps in UTC, while the database's built-in clock function returns its own machine's local time — seven hours ahead. Comparing the two shifts every threshold by that difference. A cleanup job briefly swept at seventeen hours instead of twenty-four.

What those defects changed

  • Nothing counts as done until it has been run. Anything touching the screen is exercised in a browser with the controls actually clicked, not through an API script.
  • A test must have been seen failing. A test that has never been red has not tested anything. More than once a “passing” test turned out to be passing over an empty array.
  • Tests seed through the same path the application uses. A test that seeded through a different connection once passed over broken code twice, in opposite directions — it was not testing the application, it was testing itself.
  • Check the thing that can actually break, not the nearest thing that is easy to see. A security policy was once declared safe because the page “still looked styled” — what got checked was the background colour, while what had broken was the typeface.

Security review

Once documents and notifications were finished, the whole of it was reviewed for security before signups opened to the public. Five findings, all now closed: orphaned files in storage, a sweeper that reported success while objects remained, the two most destructive endpoints turning out never to have been exercised by any test, an unsubscribe link an email scanner could press instead of the person, and a notification address that could be pointed at someone else without their consent.

Isolation between users is tested as a requirement, not a nicety. One test file must be updated whenever an endpoint is added: two accounts are created, then one tries to touch the other's data at every endpoint. An endpoint missing from that file counts as unfinished.

Surprises from the production environment

  • Production runs three Node processes, each with its own scheduler. Every job that sends something therefore has to claim its work atomically before acting — otherwise one event produces three emails.
  • The web server in front of Node overwrites security headers. The policy that actually applies ended up declared inside the page rather than as a header.
  • File count grows faster than traffic does.

Still open

Sessions cannot be revoked server-side: signing out only discards the cookie in the browser, so a stolen session stays valid until it expires. That is admitted plainly on the privacy page, along with the way out of it. Writing it down felt more honest than staying quiet.
